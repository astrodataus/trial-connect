# Trial Connect: Hand-off

Written 2026-08-22, for continuation in a fresh session (Claude Cowork or otherwise) with zero prior context on this project.

## What this is

Trial Connect is a clinical study connector for a value-based oncology network. It helps an oncologist or care navigator shortlist recruiting clinical trials for a patient, see exactly why each trial surfaced, and act on it. It's a static/embedded-data web app built from a real ClinicalTrials.gov snapshot, with no backend server.

**Live:** https://astrodataus.github.io/trial-connect/
**Repo:** https://github.com/astrodataus/trial-connect (public)

Currently generically branded, no client name anywhere in the app or copy. See "Business context" below for why that matters.

## The one rule that governs every design decision here

**The app never asserts eligibility.** It produces a shortlist with reasons, not a verdict.

- Hard, checkable facts (age, sex, tumor-type relevance, recruiting status, distance to nearest site) may filter a trial out of the shortlist.
- Anything parsed from eligibility prose (ECOG, biomarkers, prior lines of therapy) is a labelled suggestion shown next to the verbatim source sentence, and it **never filters** the shortlist; only hard facts do.
- Near-misses (excluded by exactly one hard filter) are shown with that single excluding reason. This is deliberately the most useful row on the screen: something a navigator can resolve with a phone call.
- **No eligibility scores or probabilities anywhere.** Ranking is by distance to nearest site (a real, checkable number), never an invented figure.
- Every view has the footer: *"A search tool, not a clinical decision tool. Trial data from ClinicalTrials.gov."* plus a snapshot-date line.

If you extend this app, any new feature has to fit inside this rule. It's the thing a clinical/compliance reviewer will check first.

## How to run everything

```bash
python3 -m venv .venv && source .venv/bin/activate
pip install -r requirements.txt
python3 -m playwright install chromium

python3 fetch.py              # re-pull the ClinicalTrials.gov snapshot (rate-limit-polite, re-runnable)
python3 parse_criteria.py     # re-parse eligibility criteria -> data/criteria_signals.csv
python3 -m pytest tests/ -v   # 23 unit tests, all passing
python3 build.py              # -> dist/, standalone.html, app-omni.html
python3 verify.py             # serves dist/ over HTTP, 20 Playwright checks, writes screenshots/
```

To redeploy after any change: commit, push to `main` (paths touching `dist/**` auto-trigger `.github/workflows/deploy-pages.yml`), or `gh workflow run deploy-pages.yml --repo astrodataus/trial-connect`.

## Data: what's really in the snapshot, and the scoping decision

Fetched from `https://clinicaltrials.gov/api/v2/studies` (public domain, no key), `filter.overallStatus=RECRUITING`, four `query.cond` searches (breast cancer, non small cell lung cancer, colorectal cancer, prostate cancer), all US sites, snapshot dated 2026-08-22.

**Important finding, still true today:** 63% of the raw 5,980 studies have zero US sites in this snapshot (global trials with only ex-US arms, or basket trials where the tumor type is one of many conditions listed). Those rows stay in `data/studies.csv` as the honest public record, but the app's matching population (Match / Map / Landscape) is scoped in `build.py` (`matching.is_active`) to the **2,205 studies with at least one geocoded US site**. If you re-fetch and this ratio changes a lot, it's worth re-examining whether the scoping rule still makes sense.

Soft-signal coverage in the parsed criteria (word-boundary regex, not an LLM): ECOG mentioned in ~49% of criteria; HER2 in 1,090+ studies, EGFR 800+, PD-L1 540+, ALK 630+, and so on for the other ~12 tracked biomarker tokens. One thing worth knowing if you touch `parse_criteria.py`: a case-insensitive `MET` match will catch the common word "met" ("criteria must be met"); it's handled with a case-sensitive rule for that one token specifically (see `_CASE_SENSITIVE_TOKENS` in `parse_criteria.py`), found and fixed via the unit tests, not by inspection.

## Matching engine (matching.py, mirrored line-for-line in app.js)

For a patient and an active study sharing the same tumor type:

- **Hard filters** (any one failure alone -> near-miss with that reason; two or more failures -> excluded entirely, doesn't appear anywhere): sex, structured age bounds (parsed from `minimumAge`/`maximumAge`), distance to nearest geocoded US site vs. the patient's travel radius (haversine).
- **Soft chips** (informational only, shown on matches, never filter): ECOG fit/mismatch, biomarker mention with positive/negative/unspecified qualifier (and whether it's in an inclusion or exclusion section of the criteria), prior-therapy line-count comparison including treatment-naive.
- **Ranking**: ascending distance to nearest site. No score.

This logic exists in two places on purpose: `matching.py` (Python, used by `build.py` to precompute the 8 canonical demo patients' shortlists, and by `verify.py` to independently recompute figures from raw CSVs) and the JS mirror in `app.js` (`TC.match.matchPatient`), which runs live in the browser so the "edit patient attributes" panel on the Match view can recompute a shortlist for an edited profile without a server round-trip. **If you change the matching rules, change both, and re-run `verify.py`**: it will catch a mismatch because it compares recomputed-from-raw-CSV figures against the rendered page.

## Design system

"Astrodata Taliesin West Midnight." Dark by default (`paper #0E1116`, `ink #E8E2D2`), light theme toggle persisted to `localStorage`. Marigold `#E8A33D` as the single accent (active state / primary action / focus ring only). Terracotta `#B5563A` = negative/excluded, ocotillo `#8AA66B` = positive/match, turquoise `#6FA8A0` = spare/neutral. Jost 200 uppercase headlines, Source Serif italic for editorial deks, JetBrains Mono for every uppercase label, system sans for body. Line icons at 1.5px stroke, no emoji. House style: curly quotes always, no em dashes (checked and fixed twice already; grep for an em dash in any new copy before committing), never a number on screen that wasn't computed from the data.

## Known gaps / things the next session should know are incomplete

1. **`app-omni.html` is a stub, not a real Omni integration.** The data layer is isolated behind `window.omni.query()` so a real integration is a small, contained change, but as of this hand-off there is no MCP/API connection to any live Omni workspace. See memory: `omni-integration-gap`.
2. **The Match view caps display at 25 matches / 10 near-misses per patient** (`DISPLAY_MATCH_LIMIT`/`DISPLAY_NEAR_MISS_LIMIT` in `build.py`) even though raw counts run into the hundreds for some profiles (e.g. Patient A: 258 matches, 644 near-misses) because tumor-type relevance is a loose condition-text match including basket trials. This is disclosed via the "Matches · N" count header but the list itself is truncated silently past the cap. Worth deciding if pagination or a smarter default filter is wanted.
3. **The Map view's distance rings (25/50/100 mi) are a schematic approximation**, not true great-circle circles in Albers projection space, explicitly labelled "(schematic)" in the legend. Real distance figures shown as text elsewhere (Match, Study) are exact haversine, not approximated.
4. **Standalone.html and app-omni.html are ~16MB each** (all active-cohort data embedded). Works fine as a "opens with no network" deliverable but is not a small download.
5. No automated re-fetch schedule; the snapshot is static until someone runs `fetch.py` again by hand.
